항목변경과 영향
법적 보존 게이트검토 미확인·무효화된 검토·보존 대상은 제목과 파일을 보존합니다. 권한 있는 검토자의 명시적 검토와 근거 식별자가 있어야 진행합니다. 검토 권한이나 “보존 의무 없음” 결정을 기본으로 만들지 않았고 법정 기간도 정하지 않았습니다.
과거 URL 게이트legacy 결과물은 원본·대표 이미지의 기존 차단 및 CDN 확인이 완료돼야 진행합니다. origin-only 테스트를 CDN 완료로 승격하지 않습니다. 새 게이트웨이만 사용한 결과물은 삭제로 차단된 서버 권한을 확인합니다.
제목 정리삭제 결과물의 발행 당시 편물명 스냅샷과 수정 제목만 지웁니다. 원본 projects.name과 활성 발행물은 보존합니다. 제목 정리 실패는 파일 상태와 별도로 기록·재시도합니다.
객체별 물리 정리서버의 고정 manifest에서 JPEG·합성 MP4·성장 MP4와 대표 이미지를 하나씩 처리합니다. 회수로 생긴 대체 경로도 포함합니다. 폴더·와일드카드·클라이언트 지정 경로는 허용하지 않습니다.
안전장치Storage 삭제 트랜잭션 안에서 보존 결정 버전·삭제 상태·정확한 경로·다른 참조를 다시 확인합니다. 검토 변경과 삭제를 잠금으로 직렬화합니다. 정리된 경로 재업로드도 차단합니다. 기존 계정 전체 삭제 경로는 유지합니다.
재시도와 부분 성공객체당 최초 포함 최대 6회. 직전 실패 완료부터 1분·5분·15분·1시간·3시간 후 추가 시도합니다. 성공 객체는 재삭제하지 않습니다. 보류는 실패 횟수로 세지 않고, 임대 만료도 한도 내에서 복구합니다. 링크 회수와 작업·카운터·스케줄을 분리합니다. 예약 지연 시간도 기록합니다.
원본·tombstoneprojects·posts·촬영 원본과 다른 발행 결과물은 변경하지 않습니다. 결과물 ID·제작 에디션·삭제 상태·유일성 제약과 최소 감사 이력은 유지해 재발행을 막습니다.
상태 화면과 감사내 결과물 → 삭제 결과물 정리 상태에서 제목/객체별 보류·부분 성공·한도 소진을 표시합니다. 삭제 제목·미디어·경로·토큰·법적 검토 근거는 반환하지 않습니다. 완료된 링크의 서명 검증 URL 사본은 제거하고 증명 시각·상태를 유지합니다.

분리 환경 검증

실제 일회용 Supabase에서 JPEG·합성 MP4·성장 MP4와 대표 이미지 6객체의 Storage 부재와 내부 물리 파일 삭제, 제목 정리, 원본 posts·프로젝트·다른 발행물 보존, 삭제 미디어 재발급 차단, 텍스트 전용 상태 화면을 확인했습니다. 앱을 닫은 뒤 실제 pg_cron/pg_net이 두 객체를 각각 최초 1회로 정리하는 것도 통과했습니다. 기존 웹 회귀 30개도 모두 통과했습니다. 이후 보존 검토 무효화 게이트를 보강한 코드 87c8283도 실제 Supabase에서 SQL 206건·기존 P0·구URL 회수·결과물 정리·앱 종료 후 예약 검사를 재실행해 통과했습니다. 웹 코드가 같고 앞서 통과한 전체 30개는 이 후속 실행에서 중복 실행하지 않았습니다. 최종 보강 검증 · 전체 30개 포함 검증

새 SQL 검사는 보존 미확인·hold·권한 위조·직접 제목 변경·거짓 부재 응답·부분 성공·6회 상한·정확한 간격·임대 만료·제목 실패 독립 재시도·legacy 대체 경로·재업로드 차단을 포함합니다. SQL에서 만든 confirmed manifest는 상태 전이 검사 전용이며 실제 CDN 증거가 아닙니다. 장기 재시도 간격은 가상 자료의 예약 시각 차이로 검증했으며 4시간 21분을 실시간 대기한 시험은 아닙니다.

새 단위 검사는 잘못된 경로·비인가/임의 본문·응답 유실·파일 잔존·HTML 404·401/403/5xx를 검사합니다. 중첩 DB 검사는 중복 claim·보존 변경과 삭제·중복 완료의 실제 겹침을 확인했습니다.

Storage API v1.84.19의 공식 삭제 구현에서 DB 트랜잭션 안의 객체 삭제 순서도 확인했습니다. 실제 Storage API에서는 작업을 잡은 뒤 보존 결정을 hold로 바꿨을 때 삭제가 거부되고 파일이 남는 것을 확인했습니다.

전용 환경에 적용할 구성

  1. 새 0025_result_cleanup.sql을 이전 마이그레이션 뒤에 적용합니다. 이 작업에서는 운영 적용을 수행하지 않았습니다.
  2. cleanup-results 함수에 별도 32자 이상 서버 비밀키 CLEANUP_WORKER_SECRET을 설정합니다. 사용자 앱에 넣지 않습니다. 요청 본문은 비어 있어야 하며 호출자가 작업 대상을 고를 수 없습니다.
  3. 테스트 환경 Vault의 knitting_cleanup_function_url과 knitting_cleanup_worker_secret을 구성하고 supabase/ops/schedule_result_cleanup.sql을 설치합니다. 매분 최대 3개 호출이며 앱과 독립적으로 동작합니다. 같은 결과물은 한 객체씩 처리하므로 원본/대표 이미지 정리에 예약 주기가 두 번 필요할 수 있습니다.
  4. 실제 권한 승인과 보존 검토 후에만 검토자를 등록하고 review_result_retention으로 검토 결과와 최소 근거 식별자를 기록합니다. 이 테스트에서는 가상 계정에만 임시 권한과 가상 결정을 만들었습니다. 새 운영자 화면이나 수동 재처리 기능은 추가하지 않았습니다.
  5. Storage 버전 보존/보관 기능이 켜져 있으면 자동 완료를 허용하지 않습니다. 테스트한 API 버전과 다르면 삭제 트랜잭션·물리 파일·보존 변경 경합을 다시 확인해야 합니다. 검토 변경은 이미 삭제된 데이터를 되돌릴 수 없습니다.

제목·로그·백업의 남은 범위

현재 코드에서 삭제 제목의 서버 사본은 두 결과물 필드이며 정리 상태 DTO와 새 감사 이력에는 복제하지 않습니다. 정리 화면 캐시는 비활성화 시 폐기합니다. 링크 위험 조회도 비활성 캐시를 폐기하며 기존 60초 이벤트 재조회·수동 확인 정책을 유지합니다. 이미 표시 중인 응답은 다음 성공 응답 전까지 남을 수 있습니다. 상시 폴링은 추가하지 않았습니다.

별도 검색 색인은 현재 코드에서 발견되지 않았습니다. 플랫폼의 Storage/DB 요청 로그·내보낸 보고서·백업 사본과 보존 주기, 법적 접근 권한은 운영 설정을 변경하거나 조사하지 않았으므로 실효 삭제 완료로 단정하지 않습니다. 이미 다운로드한 파일·스크린샷·기기 캐시와 영상에 합성된 글자도 이 서버 제목 정리만으로 회수되지 않습니다.
