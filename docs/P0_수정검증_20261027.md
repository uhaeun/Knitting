# 출시 전 P0 수정 후보 — 2026-10-27

**현재 출시 판정은 보류다.** 이 변경은 우선순위가 높은 인증·권한·삭제/복원·발행 경로를 수정한 후보이며 79개 요구사항 전체 구현 완료가 아니다. 기존 정책을 축소하거나 P1/P2로 재분류하지 않았다. 운영 DB·실사용자 데이터·운영 Auth 설정을 변경하지 않았다.

## 변경과 영향

- AUTH-007~011: `change-username` 함수가 원래 사용자 JWT를 Auth에서 검증하고, 그 사용자의 현재 비밀번호를 다시 확인한 뒤 service 전용 DB 함수를 호출한다. 클라이언트의 대상 UUID·최근 로그인 표시·재인증 완료 플래그는 신뢰하지 않는다. UUID는 유지하고 첫 변경은 바로 허용, 이후 720시간 제한·옛 이름 영구 예약·실패 시 롤백을 적용한다. 과거 변경 시각을 추측하여 채우지 않는다.
- AUTH-003/005: MVP 소셜 버튼은 서버 제공자 설정과 독립적으로 숨긴다. 기존 소셜 계정/제공자는 변경하지 않는다. 생성 폼을 새로 열 때마다 나만·오늘로 초기화한다. 비공개 계정·프로젝트·승인 팔로워·차단 조건을 서버에서 검사한다.
- PROJ-001~006/021: 기기의 IANA 시간대와 서버 시각으로 날짜를 검증한다. 공개 범위·삭제·복원은 전용 트랜잭션만 허용한다. 복원 시 프로젝트·함께 삭제한 기록·활성 발행물을 private로 만든다. 새 삭제 작업 ID로 함께 지운 기록을 구분하며 ±2초 추정 복원을 제거했다. **과거 삭제 작업 ID가 없는 기록은 자동 복원하지 않는다.** 실제 과거 관계 확인 없이 개별 삭제 기록을 살리지 않기 위한 제한이다.
- PROJ-007~020: 원본 편물 삭제 후 활성 발행물을 유지하고, 일반 사용자 hard DELETE·발행물 undelete·타인 프로젝트 참조를 차단한다. 발행 당시 이름/수동 제목, 내 결과물 목록·열람·삭제·삭제 편물의 개별 공개 변경을 추가했다. 제목 변경은 파일을 재인코딩하지 않는다. 새 발행은 제작 버전 ID로 중복·응답 유실을 처리한다. 명시적 다시 제작만 별도 버전을 만든다. **제작 버전이 없는 과거 발행물은 버전을 추측하지 않고 명시적 다시 제작을 요구한다.**
- 두 기기에서 같은 제작 버전을 발행할 때 실패한 요청이 성공한 파일을 지우지 않도록, 결과물 경로는 클라이언트 덮어쓰기/삭제를 서버 트리거로 차단한다. 일상 촬영 실패 업로드 정리는 유지한다. 결과물의 미발행 업로드는 보존하고 서버 정리 작업으로 넘겨야 하며, 해당 정리 워커는 아직 미구현이다.
- 성장 MP4도 생성·저장과 분리된 명시적 피드 발행을 사용한다. 원본 캡처·기기 저장 경로는 유지한다.
- 새 결과물 URL: `revocable-media`가 HMAC 서명·만료·발행 버전·현재 계정/팔로우/차단/공개 범위를 매 요청 검증한다. 파일과 썸네일 모두 적용하며 Range와 no-store를 지원한다. 인증된 사용자도 결과물의 Storage 서명 URL을 직접 발급할 수 없다. URL 갱신·계정 전환·권한 변경의 늦은 응답이 캐시를 되살리지 못하게 한다.
- **과거 Storage 서명 URL은 이 코드만으로 회수 완료라고 표시하지 않는다.** 기존 결과물은 legacy 위험 표시를 유지하며, 삭제 결과물도 제목/시각/유형만 반환하는 별도 문제 목록에 포함한다. 위험 조회 실패는 0이 아니라 확인 불가다. 자동 HTTP 조회는 계정별 1분 간격으로 제한하고 수동 재확인을 제공한다.
- 계정 삭제는 클라이언트 폴더 순회 대신 `delete-account` 서버 작업이다. photos·avatars의 본인 파일만 열거하며 파일 제거 후 다시 남은 객체를 조회한다. 잔존 객체가 있으면 Auth 삭제를 거부한다. 부분 실패는 상태·계정을 유지하고 재시도한다. 삭제 요청 이후 새 업로드를 차단한다. 계정 삭제와 구URL/CDN 회수는 별개 검증이다.

## 테스트/배포 구성 주의

새 후보는 `0015`~`0023`이며 이미 적용된 `0001`~`0014`를 수정하지 않았다. 운영 적용이나 배포는 수행하지 않는다.

`change-username`, `delete-account`, `revocable-media`와 마이그레이션·새 클라이언트는 함께 검증해야 한다. 게이트웨이 GET만 HMAC 검증을 사용하여 `verify_jwt=false`이며 POST는 별도로 Auth JWT를 검증한다. 다른 두 함수는 JWT 검증을 유지한다. service-role 키와 미디어 비밀키는 서버 전용이다.

로컬 함수 예시 설정은 `supabase/functions/local.example.env`를 참고한다. `MEDIA_SIGNING_SECRET`은 32자 이상 임의 값이며 테스트·운영을 분리해야 한다. 로컬 컨테이너의 내부 API 주소와 브라우저에서 접근하는 공개 API 주소가 다르므로 `MEDIA_PUBLIC_URL`을 명시한다. 비밀키를 앱의 EXPO_PUBLIC 변수로 넣지 않는다.

Storage 읽기 정책을 먼저 바꾸면 이전 클라이언트의 결과물 이미지/발행이 동작하지 않을 수 있다. 기존 설치 앱·캐시된 웹 버전과의 전환, 과거 잘못된 파일 경로/표시 이름, 마이그레이션 적용 버전은 별도 읽기 전용 사전 점검이 필요하다. 확인되지 않은 운영 데이터를 자동 보정하지 않는다. 실제 배포 순서·업데이트 안내와 잔여 P0가 정리되기 전 main 병합/운영 적용을 하지 않는다.
