01만들려는 것

Knitting(닛팅)은 뜨개 편물을 같은 각도로 찍어 쌓고, 그 사진들을 이어붙여 편물이 자라나는 영상을 자동으로 만들어 주는 앱입니다. 여기에 팔로우 · 피드 · 댓글 같은 소셜 기능이 붙습니다. iOS와 Android 동시 출시가 목표입니다.

기존 뜨개 앱(닛다, cromu, Knitflow, 실노트, 닛로그)은 전부 사진을 프로젝트에 딸린 첨부물로 취급합니다. 사진 자체가 주인공이고 그게 영상이 되는 앱은 없었습니다. 거기가 이 앱의 자리입니다.

항목선택
앱Expo (React Native) + TypeScript — 코드 한 벌로 양 플랫폼
백엔드Supabase (인증 · 데이터베이스 · 저장소)
영상기기 안에서 직접 인코딩. 이것만 플랫폼별 코드가 필요합니다

02우리 둘이 하는 일

코드는 Claude(AI 코딩 도구)가 씁니다. 화면도 로직도 데이터베이스도요. 그래서 우리 둘은 손으로 코드를 짜는 대신 무엇을 만들지 정하고, 만들어진 걸 검증하고, 고칠 것을 찾는 일을 합니다.

주체담당
Claude화면 · 로직 · 데이터베이스 · 테스트 코드 작성
우리 둘기획 판단, 테스트 설계, 실사용 검증, 버그 · 개선점 발굴, 우선순위 결정
하은위 + iPhone 검증 + 콘솔 작업(Apple · Google · Supabase)
다희 매니저님위 + Android 검증

둘 다 QA를 하고 있다는 게 이 구조에 잘 맞습니다. AI가 코드를 쓰는 상황에서 가장 부족해지는 게 "이게 맞는지 판단하는 사람"인데, 그게 우리 본업이니까요.

실제 진행 방식

Claude가 기능 구현 → 무선 업데이트로 배포 (1~2분) → 다희 매니저님 Android / 하은 iPhone 에 최신 버전 → 각자 실제로 뜨개하면서 써 봄 → "이게 불편하다" / "여기서 터진다" → GitHub Issue → 다시 위로

배포는 주 2회 정도로 잡고 있습니다. 매일이면 써 볼 틈이 없고, 주 1회면 너무 느립니다.

화면이나 로직만 바뀌면 앱을 껐다 켜는 것만으로 최신 버전이 됩니다. 매번 새로 설치하실 필요 없습니다. 카메라 같은 기기 기능이 추가될 때만 재설치가 필요하고, 그건 드뭅니다.

가장 중요한 부탁 — 실제로 써 주세요

각자 실제 편물 하나를 이 앱으로만 기록해 주셨으면 합니다. 매일 한 장 이상. 이걸 안 하면 무엇을 고쳐야 할지 알 수가 없고, 위 루프가 빈 껍데기가 됩니다.

기록 앱의 진짜 적은 경쟁 앱이 아니라 "귀찮음"입니다. "오늘 찍기 귀찮았다"가 가장 값진 피드백입니다. 그런 순간이 오면 그대로 이슈로 남겨 주세요. 버그보다 중요합니다.

이슈 쓰실 때

  • 무엇을 하려 했는지 / 무엇이 일어났는지 / 무엇을 기대했는지
  • 재현 순서 (가능하면)
  • 스크린샷 또는 화면 녹화
  • 기기 모델과 OS 버전

익숙한 형식이실 테니 편하신 대로 쓰셔도 됩니다.

03첫 세션에서 같이 할 것

혼자 시작하실 필요 없습니다. 첫 세션은 같이 앉아서 진행합니다. 여기서 정한 것이 이후 모든 코드의 기준이 되기 때문에, 나눠서 하면 안 되는 것들입니다.

30분설계 문서 같이 훑기 — 무엇을 만들지 합의
50분데이터베이스 구조 같이 검토 — 한 번 정하면 되돌리기 어렵습니다
40분공개 범위 · 차단 규칙 검토 — 이 앱은 서버가 따로 없어서 여기가 보안 전부입니다. QA 관점의 조합 매트릭스를 같이 만듭니다
20분도그푸딩 규칙 · 이슈 작성 규칙 · 배포 주기 합의
20분각자 개발 환경 셋업, 빈 앱이 각자 기기에서 뜨는지 확인

총 세 시간 정도입니다. 부담되면 두 번으로 나눠도 됩니다. 다만 데이터베이스 구조와 공개 범위 규칙은 반드시 같이 봐 주세요.

세 번째 항목이 특히 그렇습니다. 게시물 공개 범위(나만 / 팔로워만 / 전체) × 비공개 계정 × 팔로우 승인 대기 × 차단이 겹치는 조합이라, 눈으로는 검증이 안 되고 테스트로 고정해야 합니다. 딱 우리가 평소에 하는 일입니다.

04첫 관문 — 영상이 되는지 확인하기

본 개발에 들어가기 전에 통과해야 할 검증이 하나 있습니다. 개발 용어로 스파이크(spike)라고 합니다.

스파이크가 무엇인지

답을 모르는 기술 질문 하나에, 답만 얻으려고, 시간을 정해놓고 하는 실험입니다. 산출물이 완성된 기능이 아니라 결정이라는 점이 다릅니다. 패치 검증 들어가기 전에 "이 이슈가 우리 환경에서 재현이나 되는가"만 먼저 확인하는 것과 같은 성격입니다.

일반 개발스파이크
목적동작하는 기능을 만든다질문에 답한다
코드 품질유지보수 가능해야 함버릴 코드. 구조 · 예외 처리 신경 쓰지 않음
완료 조건인수 기준 통과답이 나옴 (된다 / 안 된다 둘 다 정상)
기간필요한 만큼미리 정한 만큼. 넘기면 중단

질문과 그 무게

질문은 하나입니다. 사진 30장을 기기 안에서 1080×1080 MP4로 만들 수 있는가.

사진을 이어붙여 새 영상을 만드는 기능이 React Native 생태계에 없습니다. 예전에는 FFmpegKit이라는 라이브러리가 그 역할을 했는데 2025년 4월에 은퇴했고, 대체재를 찾아봤지만 재생 · 압축 · 썸네일용만 있었습니다. 그래서 이 기능만 직접 만들어야 하고, 만들어 봐야 되는지 알 수 있습니다.

결과이 앱은차별점
된다편물 성장 타임랩스 앱고스트 촬영 + 자동 영상
안 된다뜨개 사진 앨범 + 피드사실상 없음

부담 갖지 않으셔도 됩니다. "안 된다"도 정확히 같은 가치를 가진 결과입니다. 화면 20개를 다 만든 뒤에 발견하는 것보다 훨씬 좋은 결말이고, 그래서 제일 먼저 합니다.

코드는 이미 Claude가 작성해 두었습니다. 빌드해서 기기에서 돌려 보고 측정하는 일입니다.

05실행 절차

첫 세션에서 같이 하거나, 편하시면 미리 해 보셔도 됩니다.

준비
git clone https://github.com/uhaeun/Knitting.git
cd Knitting
npm install

# 기기 기능이 포함되어 있어 개발 빌드가 필요합니다
npx expo login
npx expo prebuild --clean
eas build --profile development --platform android

# 검증용 이미지 30장 생성
node scripts/make-fixtures.mjs assets/fixtures 30 1080

Windows PowerShell이어도 위 명령은 동일합니다. Expo 계정은 무료로 충분합니다.

빌드가 끝나면 app/spike.tsx의 FIXTURES 배열에 frame_000부터 frame_029까지 30줄을 채웁니다. 이 부분은 Claude에게 시키셔도 되고 하은이 미리 채워 둘 수도 있습니다.

실행과 측정

앱을 띄우고 /spike 화면에서 실행 버튼을 누르면 소요 시간 · 파일 크기 · 프레임 수가 화면에 표시되고 결과 영상이 앨범에 저장됩니다.

측정 기기가 중요합니다. 인코딩은 기기 성능 편차가 가장 큰 작업이라, 최신 기기에서만 재면 반드시 놓칩니다. 가지고 계신 것 중 가장 느린 기기로 재 주세요. 2~4년 된 중저가 기기가 오히려 좋습니다.

결과 회수와 자동 검증
adb pull /sdcard/Movies/spike-android.mp4 .

# 개발 머신에만 ffprobe가 필요합니다 (앱에는 들어가지 않습니다)
#   macOS    brew install ffmpeg
#   Windows  winget install Gyan.FFmpeg

node scripts/verify-output.mjs spike-android.mp4

해상도 · 프레임 수 · 재생 길이 · 회전 정보를 자동으로 PASS/FAIL 판정합니다. 하은의 iOS 결과물과 나란히 넣으면 플랫폼 간 대조까지 해 줍니다.

07막힐 만한 지점을 미리 적어둡니다

Kotlin 코드는 아직 한 번도 컴파일해 보지 않았습니다. 첫 빌드에서 오류가 나는 것은 정상 과정입니다. 오류가 나면 그대로 붙여서 공유해 주시면 Claude가 고칩니다.

속도 — 가장 가능성이 높습니다

현재 구현은 이미지의 색상값을 영상 포맷으로 변환하는 계산을 소프트웨어로 합니다. 1080×1080 한 장이 약 116만 픽셀이고 30장이면 3,500만 회 연산이라, 저사양 기기에서는 이 부분만 수 초가 나올 수 있습니다.

7번 기준(10초)을 못 넘기면 GPU가 변환을 대신하는 방식으로 바꾸는 것이 다음 수순입니다. 이 판단이 필요해지면 같이 정하시죠.

색 — 뒤집혀 보이면 이 문제입니다

기기마다 코덱이 받아들이는 색 데이터 배치가 달라서, 결과 영상에서 붉은 실이 파랗게 나오는 식일 수 있습니다. 그러면 색 평면 순서 문제이고, 실제 포맷을 확인해서 분기하면 됩니다.

08기간과 중단 규칙

타임박스 3일입니다. 양 플랫폼 합계 기준입니다.

시간 제한을 미리 정해 두는 이유는, 이게 없으면 "하루만 더 하면 될 것 같은데"가 반복되면서 2주가 사라지기 때문입니다. 3일째에 결론이 없으면 그것도 결론입니다.

09확인 부탁드립니다

답 주시면 일정과 진행 방식을 확정하겠습니다.

  • 첫 세션 가능한 시간세 시간 정도. 온라인 화면 공유로 충분합니다. 나눠서 두 번도 괜찮습니다.
  • GitHub 아이디저장소 초대를 보내기 위해 필요합니다.
  • Android 실기기 모델과 OS 버전측정 기준 기기입니다. 여러 대 있으시면 가장 느린 것으로.
  • 로컬 개발 환경 OSWindows인지 macOS인지. 셋업 명령 일부가 달라집니다.
  • 지금 뜨고 계신 편물이 있으신지없으면 하나 시작해 주셔야 합니다. 도그푸딩에 실제 편물이 필요합니다.
  • 주당 투입 가능 시간대략이면 됩니다. 일정 추정에만 씁니다.

10이 검증이 끝나면

스파이크 결과가 나오면 본 개발에 들어갑니다. 순서는 이렇습니다.

시점내용
1주차스파이크 + 저장소 · 데이터베이스 셋업
2~3주차최소 동작 버전을 각자 폰에 설치. 촬영 → 저장 → 목록까지
3주차~도그푸딩 시작. 여기서부터 계속 쓰면서 고칩니다
4~6주차피드 · 소셜 · 영상 추가하면서 계속 사용
7~8주차안전 · 알림 · 약관 + 통합 QA

2~3주차에 폰에 뭐라도 깔리는 것이 목표입니다. 완성도보다 손에 쥐어지는 시점을 당기는 게 이 방식에서는 훨씬 중요합니다.

전체 설계는 별도 문서(닛팅 시스템 설계도 v1.1)에 정리되어 있습니다. 데이터 모델, 공개 범위 규칙, 화면 구조가 들어 있습니다. 첫 세션 전에 훑어보시면 좋지만, 지금 읽지 않으셔도 진행에는 문제없습니다.
