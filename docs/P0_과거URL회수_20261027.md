# 과거 URL 회수 후속 수정 — 2026-10-27

출시 보류를 유지한다. 범위는 PROJ-022~035의 과거 결과물 URL 회수·지속 경고·서버 재시도다. 운영 DB, 운영 Storage/CDN, 실제 사용자 데이터, 운영 함수·스케줄을 변경하지 않았다. 사용자에게 별도 테스트 프로젝트가 없음을 확인했으므로 실제 hosted CDN 전파는 미검증이며 로컬 통과로 대체하지 않는다.

## 변경과 영향

- `0024_legacy_link_revocation.sql`만 추가했다. 기존 0001~0023은 수정하지 않았다. legacy 결과물을 private로 전환하거나 개별 삭제·편물 복원으로 private 처리하면 같은 DB 트랜잭션에서 결과물당 1개 영속 작업·원본/대표 이미지 각각의 manifest를 만든다. 이미 private/삭제된 legacy 행의 의무도 이 마이그레이션에서 큐에 넣는다. 작업 생성 실패 시 DB 상태 변경도 실패하므로 안전 0건으로 누락하지 않는다.
- 공개 범위나 삭제가 성공한 뒤 Storage/CDN 처리가 실패해도 DB를 공개로 되돌리지 않는다. 결과물별 `pending/retrying/unverified/failed/failed_exhausted/confirmed`와 객체별 확인 시각·오류 코드·이력을 저장한다. 내부 경로·URL·토큰은 service 전용 테이블에만 있으며 소유자 DTO에는 반환하지 않는다.
- 서버 작업 순서는 소유 관계/다른 참조 확인 → 원본 바이트 SHA-256 확인 → 기존 경로의 검증용 signed URL 발급·워밍 → 새 고정 경로에 복사 → 복사 바이트 비교 → 게이트웨이 위치 전환 → 구경로 1개씩 삭제 → Storage 부재 확인 → 기존 URL의 무인증 GET/Range 재검증이다. 원본+썸네일 모두 필요하다. 미확인 복사본을 덮어쓰지 않고 해시가 다르면 원본을 보존한다. 복사 중 저장 공간이 일시 증가한다.
- 발행물의 기존 DB 경로/제작 에디션/tombstone은 유지한다. 별도 service 전용 manifest의 검증된 위치만 게이트웨이가 읽는다. 이미 삭제된 발행물은 새 위치가 있어도 열람·발행·서명 발급되지 않는다. 원본 posts와 다른 results를 참조하면 회수를 보류한다. 새 posts가 결과물 경로를 참조하는 우회도 차단한다.
- 회수 소스 경로와 `/revoked/` 서버 경로에는 클라이언트 INSERT/UPDATE를 금지한다. 구경로 삭제 뒤 파일을 재생성해 과거 URL이 되살아나는 것을 막는다. 계정 전체 삭제의 기존 전용 서버 경로는 유지한다. 서버 복사도 계정 활성 SHARE 잠금을 사용하여 삭제 요청 이후 새 복사본이 생기지 않도록 직렬화한다.
- `legacy_links_unverified`는 이관 대상의 인벤토리 플래그로 유지하고, 실제 위험 해제는 모든 객체를 검증한 `confirmed` 작업 상태로 결정한다. 작업 잠금 중 결과물 행을 갱신하지 않아 공개 범위 변경(result→job 잠금)과의 역순 교착을 피한다.
- 추가 자동 5회 간격은 직전 자동 실패 완료 시점부터 1분·5분·15분·1시간·3시간이다. 최초 포함 최대 6회. worker 종료도 lease 만료 실패로 영속 처리하며 무한 재실행하지 않는다. 수동 요청은 별도 카운터를 사용하고 자동 카운터/일정을 초기화하지 않는다. 자동/수동은 같은 lease와 고정 manifest로 직렬화한다. 운영자 자동 알림은 추가하지 않았다.
- 소유자는 메뉴/목록/상세에서 서버 단일 스냅샷으로 집계한 고유 결과물 위험 건수, 처리 중/조치 필요, 객체별 원본/대표 이미지 상태를 본다. 별도 문제 관리 화면에서 삭제 결과물의 텍스트·시각·유형과 수동 재시도를 제공한다. 삭제 미디어나 내부 경로를 노출하지 않는다. 조회 실패는 확인 불가이며 0건으로 바꾸지 않는다. 이미 내려받은 파일·스크린샷·기기 캐시는 회수할 수 없음을 안내한다.

## CDN 판정의 범위

`REVOCATION_VERIFICATION=origin`은 실제 구경로 제거와 기존 URL의 GET/Range 거부를 확인해도 CDN 완료로 승격하지 않는다. 로컬/설정 누락의 기본값이다. 위험과 재시도는 남는다.

`cdn` 모드의 완료에는 서버가 설정한 외부 HTTPS Storage 주소, 원본과 일치하는 기존 URL 워밍 및 실제 cache HIT 관찰, 구경로 제거 후 최소 65초 경과, 유효 기간이 남은 동일 URL의 GET/Range 접근 거부가 필요하다. 만료 URL의 4xx, 네트워크/5xx, 일부 객체 성공, Range 접근 가능, cache HIT 미관찰은 완료 근거가 아니다. 모든 객체가 확인돼야 작업을 confirmed로 한다. 검증 중에는 파일별 오류가 남으며 자동 횟수를 다 써도 경고가 유지된다.

이 판정은 해당 검사 위치에서의 관찰이다. 전 세계 모든 CDN 지점의 0초 차단이나 이미 다운로드한 파일 회수를 보장하지 않는다. 과거 실제 발급 URL의 표본/원본·썸네일·영상과 다중 위치/실기기 검증이 출시 전에 필요하다. 검증 URL은 회수 직전에 발급한 7일 유효 URL이며 과거의 모든 토큰 목록을 복원한 것이 아니다. 7일 이후 재시도에서 그 URL이 만료됐으면 안전 확인으로 취급하지 않는다.

근거: [Supabase Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn), [서명 URL](https://supabase.com/docs/guides/storage/serving/downloads). 객체 변경/삭제의 CDN 메타데이터 전파와 브라우저 캐시는 별개다.

## 분리 환경 실행

- 로컬 전용 PostgreSQL 14 하네스에 전체 24개 마이그레이션을 빈 DB부터 적용. 기존 121개 SQL + 새 회수 SQL 35개 통과. 실제 Supabase 검증과 구분한다.
- 단위 181건 통과. 새 11건은 복사 손상·원본 보호, CDN 캐시 잔존/지연, GET/Range 불일치, 만료 URL, cache HIT 미관찰, 잘못된 경로, 권한·요청 본문 제한을 검사한다. CDN 동작은 재현한 응답이며 실제 클라우드 CDN이 아니다.
- 타입·린트 경고 0·웹 export 통과. 기존 두 연결 경합 6개와 서버 복사/계정 삭제 순서를 바꾼 신규 경합 2개도 실제 중첩을 확인하고 통과했다.
- GitHub 일회용 Supabase 17에서 `supabase/tests/link_revocation.sql`, `scripts/e2e/legacy-links.ts`와 기존 P0/전체 30개 E2E를 실행한다. 실제 Storage 복사·바이트 보존·기존 URL 차단·원본 보호·새 게이트웨이 GET/Range·UI 수동 재시도·앱 종료 후 실제 pg_cron/pg_net 동작을 검사한다. 제품 코드 `aeb6ecd`의 실제 Supabase 검사에서 전체 24개 마이그레이션·서버 SQL 156건·기존 P0 인증/발행/삭제 검사·새 과거 링크 회수 검사가 통과했다. 앱 종료 후 실제 pg_cron/pg_net의 처리도 확인했다. [실행 증거](https://github.com/uhaeun/Knitting/actions/runs/40468471813). 기존 전체 E2E 30개도 모두 통과했다. 이후 JPEG·합성 MP4·삭제된 성장 MP4의 원본/썸네일 6객체 회수 검사를 확장한 `5df91ca`도 실제 Supabase에서 통과했다(제품 로직 변경 없음, 목록 행 testID만 추가). [추가 실행 증거](https://github.com/uhaeun/Knitting/actions/runs/40469292991). 삭제 성장 영상은 원본/썸네일 구URL GET/Range가 차단되고 새 미디어 발급도 0건임을 확인했다. 로컬 Storage이므로 6객체 모두 CDN 미확인 경고를 유지했다. 추가 실행에서는 이미 통과한 기존 30개를 중복 실행하지 않았다.

## 스케줄 구성과 운영 전환 조건

배포는 수행하지 않는다. 전용 테스트 환경에 먼저 0024와 새 게이트웨이·`revoke-legacy-links`를 함께 적용해야 한다. worker는 별도 32자 이상 랜덤 서버 비밀키로만 호출되며 본문으로 대상·경로·URL을 받지 않는다. 앱에 비밀키를 넣지 않는다.

`REVOCATION_STORAGE_PUBLIC_URL`은 Storage 공개 API의 origin이다. 로컬 컨테이너 안에서는 `http://kong:8000`을 사용한다. 외부 테스트 CDN에서는 정확한 HTTPS origin과 `REVOCATION_VERIFICATION=cdn`을 명시해야 한다. origin 모드로 경로를 먼저 회수하여 CDN 워밍 증거가 없는 작업은 완료를 추정하지 않는다.

스케줄은 Supabase Vault의 `knitting_revocation_function_url`, `knitting_revocation_worker_secret`을 설정한 뒤 `supabase/ops/schedule_link_revocation.sql`로 설치한다. 매분 최대 3개 worker를 호출하며 DB의 SKIP LOCKED/lease로 중복을 제한한다. 앱 실행/로그인과 무관하다. cron/pg_net/Vault가 없거나 설정이 실패하면 자동 재시도가 동작하지 않으므로 배포 완료가 아니다. API 확인과 스케줄의 실제 실행 증거를 둘 다 확인해야 한다.

## 남은 출시 차단

1. 별도 hosted 테스트 프로젝트/CDN 부재: 실제 Smart CDN 전파·다중 위치·실기기 검증 미실행. 원본/썸네일/합성 MP4/성장 MP4의 실제 CDN URL 표본 검증 필요. 운영 데이터로 대신 시험하지 않는다.
2. 원래 정책의 PROJ-036~040 제목/법적 보존·객체별 물리 정리 워커, PROJ-041~068 운영자 재처리/상태 조회는 이번 범위에서 구현하지 않았다. 회수 후 새 경로에 보존한 삭제 결과물의 파일을 정리 완료로 표시하지 않는다.
3. 과거 잘못된 경로·다른 참조·이미 사라진 소스·워밍 증거 누락·검증 URL 만료는 안전한 자동 보정을 추정하지 않고 미해결로 남긴다. 이전 클라이언트/스케줄 전환, 인증 운영 설정·동의 증거 및 이전 보고서의 기타 미확인 게이트는 유지한다.
